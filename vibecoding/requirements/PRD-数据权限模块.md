# 数据权限模块产品方案（PRD）

> 版本：v1.0  
> 日期：2026-05-12  
> 撰写：产品经理  
> 适用：DATA-CENTER 数据资产管理平台

---

## 一、背景与目标

### 1.1 背景

DATA-CENTER 当前已具备元数据管理、指标平台、SQL 查询编辑器、数据加工、智能分析（BI）五大核心能力，覆盖数据分析师、BI 工程师、业务运营、数据产品经理、数据治理人员等多类角色。

但平台目前仅有**最基础的登录鉴权**（JWT Token + 员工信息），存在以下安全隐患：
- **无功能权限管控**：所有登录用户都能看到并使用全部菜单（元数据、指标、SQL 查询、数据加工、BI），无法按角色隔离功能入口。
- **无数据权限管控**：用户一旦登录，即可查看全部数据源、全部表结构、全部指标定义，甚至执行任意 SQL。敏感数据（如用户手机号、交易金额、身份信息）完全暴露。
- **无审批与审计**：用户访问敏感数据无需申请、无留痕、无法追溯，无法满足企业合规要求。
- **无脱敏能力**：前端展示和 SQL 查询结果中，敏感字段以明文呈现。

同时，后端已预留 `cyan-dataauth` 服务（目前为空），需要明确其定位与能力建设路径。

### 1.2 目标

建设**统一的数据权限管理中心**，实现：
1. **功能权限**：按角色控制菜单、页面、按钮的可见与可操作范围。
2. **数据权限**：按用户/角色/部门控制对「数据源 → 数据库 → 表 → 行 → 列」的访问范围。
3. **数据脱敏**：对敏感字段按规则动态脱敏（掩码、哈希、截断等）。
4. **权限审批**：支持权限申请、审批、自动授权、到期回收的全流程。
5. **审计日志**：记录用户的数据访问行为，支持检索、告警、报表。

**核心价值**：让「对的人」在「对的场景」下看到「对的数据」，同时兼顾效率与安全合规。

## 二、竞品分析

### 2.1 字节大数据平台（内部实践）

| 维度 | 方案要点 |
|------|---------|
| 资源定义 | 将数据库、表、行列权限打包为「资源包」，统一授权管理 |
| 授权主体 | 个人、部门、应用账号、用户组 |
| 审批机制 | 智能审批模型（人员风险 + 资源风险 + 关联风险），低风险自动审批，高风险人工审批 |
| 权限回收 | 冗余权限自动识别与回收，权限到期提醒与自动释放 |
| 亮点 | 10万小时审批时长节省；工单驳回率比纯人工高7% |

### 2.2 阿里云 Dataphin

| 维度 | 方案要点 |
|------|---------|
| 行级权限 | 按字段组合配置管控规则（文本/数值类型），单权限最多500条规则 |
| 关联表 | 单权限最多关联50张表，批量搜索添加 |
| 申请入口 | 用户侧「我的权限」页面主动申请，支持个人账号、生产账号、用户组 |
| 管控范围 | 离线研发、分析、数据预览、离线集成；API 调用不受行级权限管控 |
| 超级管理员 | 拥有所有行列权限，不受管控 |

### 2.3 阿里云 DataWorks

| 维度 | 方案要点 |
|------|---------|
| 权限模型 | RBAC，与 MaxCompute RBAC 天然映射 |
| 安全模式 | 标准模式下生产环境默认无任何读写权限，需主动申请 |
| 列级控制 | Label 权限控制（给列打安全标签，按标签授权） |
| 数据下载 | 安全中心可开启数据下载控制，防止数据泄露 |

### 2.4 Apache Ranger（开源标杆）

| 维度 | 方案要点 |
|------|---------|
| 策略类型 | Access Policy（允许/拒绝）、Masking Policy（脱敏）、Row-level Filter Policy（行过滤） |
| 管控粒度 | 库 → 表 → 列 → 行 |
| 脱敏规则 | 部分掩码、哈希、截断、日期取整、自定义表达式等 |
| 审计能力 | 全量访问事件记录到 Solr/RDBMS，支持实时检索与告警 |
| 集成范围 | Hive、Spark、Presto、HBase、Kafka、Doris、StarRocks 等 |
| 局限 | 纯管理员视角，无用户自助申请入口；用户权限视图极差；策略多后管理成本高 |

### 2.5 网易大数据安全中心（基于 Ranger 增强）

| 维度 | 方案要点 |
|------|---------|
| 产品定位 | 一站式安全管理平台 = 权限 + 脱敏 + 审计 + 扫描识别 + 加密 |
| 脱敏增强 | 泛化脱敏规则（如「电话号码脱敏」），白名单机制（白名单 > 脱敏），扫描脱敏一体化 |
| Owner 语义 | 表负责人递归拥有路径下所有子目录/子表权限，减少 Policy 数量 |
| Spark 支持 | 侵入 Spark 执行计划（analyzed 阶段注入 Filter + UDF，optimized 阶段鉴权） |
| 阶段演进 | Ranger 工具 → 数据中台权限模块 → 独立一站式安全平台 |

### 2.6 竞品结论与我们的策略

```
┌─────────────────────────────────────────────────────────────┐
│  不做 Ranger 的「纯管理员视角」，而是「管理员 + 用户双视角」   │
│  不做 Dataphin 的「仅管控计算引擎表」，而是「元数据层统一管控」│
│  不做字节的「全智能审批」，一期先做「标准审批流 + 简单自动审批」│
└─────────────────────────────────────────────────────────────┘
```

**差异化策略**：
- **元数据驱动**：权限策略与元数据表、主题域、业务数据库天然关联，而不是孤立配置。
- **双视角设计**：管理员侧（策略配置、审批管理、审计监控）+ 用户侧（我的权限、一键申请、数据预览自动生效）。
- **SQL 层拦截**：与 SQL 编辑器、数据加工引擎联动，查询前自动改写 SQL（注入 WHERE + 脱敏函数）。
- **渐进式建设**：一期聚焦「功能权限 + 表级/列级权限 + 基础审批」，二期扩展「行级权限 + 智能审批 + 审计告警」。

## 三、用户故事

### 3.1 数据治理管理员（Admin）

> 作为数据治理管理员，我希望统一管理全平台的功能权限和数据权限，按角色批量授权，并查看权限使用情况和审计日志，以便确保数据安全合规、降低越权风险。

**典型场景**：
- 新员工入职时，按「数据分析师」角色一键授予「指标平台只读 + BI 编辑 + 业务数据库只读」权限。
- 发现某张订单表被频繁访问，查看谁有权限、谁实际访问过、访问了哪些字段。
- 配置「用户手机号」字段全平台脱敏，仅「风控专员」角色可查看明文。

### 3.2 数据分析师

> 作为数据分析师，我希望只看到我负责业务域的数据资产，查询结果中敏感字段自动脱敏，当我需要更多权限时可以自助申请并快速获得审批，以便高效、安全地完成分析工作。

**典型场景**：
- 打开 SQL 编辑器，左侧数据源树只显示「华东大区」相关的数据库和表。
- 查询用户表时，`phone` 字段自动显示为 `138****8888`，`id_card` 显示为 `**************1234`。
- 需要查看「全量订单数据」做月度复盘，在「我的权限」页面提交申请，5 分钟后自动审批通过。

### 3.3 业务运营人员

> 作为业务运营，我希望在 BI 看板和指标分析页面，只能看到自己负责区域/品类的数据，看不到其他区域的数据，以便聚焦自己的业务。

**典型场景**：
- 打开「销售额趋势」指标看板，默认只筛选出「美妆品类」的数据。
- 尝试切换筛选器选择「3C 品类」，提示「无权限查看该品类数据，是否申请？」。

### 3.4 数据开发工程师

> 作为数据开发，我希望在数据加工（SparkSQL/FlinkSQL）任务中，生产环境的数据访问受到严格控制，开发环境权限相对宽松，以便安全地开发和发布任务。

**典型场景**：
- 在开发环境编辑 SparkSQL 任务，可以读取测试库全部表。
- 发布到生产环境后，任务执行时自动校验生产账号是否有目标表的读写权限，无权限则阻断并提示申请。

### 4.2 权限模型设计

采用 **RBAC + ABAC 混合模型**：

```
┌────────────────────────────────────────────────────────────────────┐
│                        权限模型（RBAC + ABAC）                      │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│   用户(User) ──→ 用户组(Group) ──→ 角色(Role) ──→ 权限(Permission) │
│      │               │                │                             │
│      │               │                └─→ 功能权限（菜单/按钮/API）  │
│      │               │                └─→ 数据权限（库/表/行/列）    │
│      │               │                                             │
│      └───────────────┴─→ 属性条件（ABAC）：部门=华东、职级≥P6 等    │
│                                                                    │
│   数据资源(Resource)：                                               │
│     ├─ 功能资源：菜单、页面、按钮、API 接口                          │
│     ├─ 数据资源：数据源 → 数据库 → 数据表 → 字段                     │
│     └─ 规则资源：行级过滤条件、列级脱敏规则                          │
│                                                                    │
│   策略(Policy)：                                                     │
│     ├─ 访问策略（Allow / Deny）                                     │
│     ├─ 行级过滤策略（Row Filter）                                    │
│     └─ 脱敏策略（Masking）                                          │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**关键设计原则**：
- **Deny 优先**：当 Allow 和 Deny 冲突时，Deny 优先（与 Ranger 一致）。
- **最小权限原则**：新用户默认无任何数据权限，需申请或授权。
- **权限继承**：角色可继承其他角色；数据权限按「数据源 → 数据库 → 表」层级继承。
- **Owner 特权**：表的负责人（Owner）自动拥有该表的全部权限（减少策略配置量）。

#### 5.1.2 角色预设

| 角色 | 功能权限范围 | 数据权限范围 |
|------|------------|------------|
| 超级管理员 | 全部 | 全部（不受限制） |
| 数据治理员 | 元数据平台全部 + 权限管理中心全部 | 全部（可配置） |
| 数据分析师 | 指标平台(只读) + SQL查询 + BI(编辑) | 按业务域授权 |
| 数据开发工程师 | 数据加工全部 + SQL查询 + 元数据(只读) | 按项目授权 |
| 业务运营 | 指标平台(只读) + BI(只读) | 按部门/区域授权 |
| 访客 | 首页 + 指标概览 | 仅限公开数据集 |

#### 5.1.3 前端控制点

- **路由守卫**：无权限访问某页面时，路由拦截并展示「403 无权限」页面。
- **菜单过滤**：顶部导航栏和侧边栏根据角色动态渲染，无权限的菜单不显示。
- **按钮级控制**：页面内「新增」「编辑」「删除」「导出」等按钮根据权限动态显隐或置灰。
- **API 拦截**：前端发送请求前校验权限（防君子），后端接口同时做权限校验（防小人）。

### 5.2 数据权限（Data Permission）

#### 5.2.1 权限层级

```
┌──────────────────────────────────────────────────────────────┐
│                     数据权限五层模型                          │
├─────────────┬────────────────────────────────────────────────┤
│  L1 数据源   │  控制用户能否看到某个数据源（如 MySQL-prod）    │
│  L2 数据库   │  控制用户能否看到某个数据库（如 order_db）      │
│  L3 数据表   │  控制用户能否看到某张表（如 orders）            │
│  L4 行级     │  控制用户能看到哪些行（如 region='华东'）       │
│  L5 列级     │  控制用户能看到哪些字段，以及是否脱敏           │
└─────────────┴────────────────────────────────────────────────┘
```

**层级规则**：
- 上层无权限则下层不可见（如 L1 拒绝则 L2/L3/L4/L5 全部拒绝）。
- L3 表级权限可单独配置「只读 / 读写 / 拒绝」。
- L4 行级和 L5 列级依赖 L3 的「只读」或「读写」权限。

#### 5.2.2 行级权限（Row-level Permission）

**配置要素**：

| 要素 | 说明 |
|------|------|
| 权限名称 | 全局唯一，如「华东大区订单数据权限」 |
| 控制字段 | 选择需要管控的字段，如 `region`、`department`、`brand` |
| 管控规则 | 规则组合支持 AND/OR 嵌套（最多3层） |
| 规则类型 | 枚举值（IN）、条件比较（= / != / > / < / LIKE）、标签匹配 |
| 关联表 | 支持一张规则关联多张同结构表（批量生效） |
| 授权对象 | 用户 / 角色 / 部门 / 用户组 |

**规则示例**：

```
规则名：华东分析师可见范围
控制字段：region（枚举值 IN ['华东']）
         AND (
           brand = '美妆' 
           OR brand = '个护'
         )
         AND create_time >= '2024-01-01'
关联表：order_db.orders、order_db.order_items
授权对象：角色「数据分析师-华东组」
```

**SQL 改写效果**：

```sql
-- 用户原始 SQL
SELECT * FROM order_db.orders WHERE status = 'completed'

-- 权限引擎改写后
SELECT * FROM (
  SELECT * FROM order_db.orders 
  WHERE region IN ('华东') 
    AND (brand = '美妆' OR brand = '个护')
    AND create_time >= '2024-01-01'
) _perm_filter_
WHERE status = 'completed'
```

#### 5.2.3 列级权限与脱敏（Column-level Permission & Masking）

**两种控制模式**：

| 模式 | 效果 | 示例 |
|------|------|------|
| 禁止查看 | 该字段对授权对象不可见（查询结果不返回该列） | `salary` 字段对普通员工隐藏 |
| 脱敏展示 | 该字段对授权对象按规则变形后展示 | `phone` → `138****8888` |

**脱敏规则库（预设）**：

| 规则名称 | 说明 | 示例（原始 → 脱敏后） |
|---------|------|---------------------|
| 全掩码 | 全部替换为 `*` | `13800138000` → `***********` |
| 手机号掩码 | 中间4位掩码 | `13800138000` → `138****8000` |
| 身份证掩码 | 中间位掩码，保留前3后4 | `110101199001011234` → `110***********1234` |
| 姓名掩码 | 保留姓，其余掩码 | `张三丰` → `张**` |
| 邮箱掩码 | 保留前缀1位和域名 | `zhangsan@cyan.com` → `z****@cyan.com` |
| 银行卡掩码 | 保留后4位 | `6222021234567890123` → `****************0123` |
| 数值取整 | 按区间取整 | `12345` → `10000`（万级取整） |
| 自定义正则 | 正则表达式替换 | 按需配置 |

**列级规则配置**：

```
规则名：用户敏感信息脱敏
关联表：user_db.users
字段规则：
  - phone → 手机号掩码（对「访客」「业务运营」生效）
  - id_card → 身份证掩码（对「访客」「业务运营」「数据分析师」生效）
  - salary → 禁止查看（对「访客」「业务运营」「数据分析师」生效，仅「HR」「财务」可见）
白名单：角色「风控专员」不受此规则限制
```

**SQL 改写效果**：

```sql
-- 用户原始 SQL
SELECT user_id, name, phone, id_card, salary FROM user_db.users

-- 权限引擎改写后（数据分析师视角）
SELECT 
  user_id,
  CONCAT(SUBSTR(name, 1, 1), '**') AS name,
  CONCAT(SUBSTR(phone, 1, 3), '****', SUBSTR(phone, 8, 4)) AS phone,
  CONCAT(SUBSTR(id_card, 1, 3), '***********', SUBSTR(id_card, 15, 4)) AS id_card,
  NULL AS salary  -- 或直接从 SELECT 中移除
FROM user_db.users
```

> **优先级约定**：行级过滤先于列级脱敏执行（即先筛选行，再对可见行脱敏）。

### 5.3 指标平台数据权限（Metric & Dimension Permission）

> **核心问题**：用户有了维度的权限，是否意味着拥有了对应的表字段权限？
> 
> **明确答案：不意味着。** 维度权限与表字段权限是两条独立的权限线，原因见下文「维度权限 vs 表字段权限」章节。

#### 5.3.1 为什么需要独立的指标平台权限

指标平台的数据权限**不能简单等同于元数据层的数据权限**，因为指标和维度是「业务语义层」的概念，与底层物理表是两层体系：

| 对比维度 | 元数据层（表/字段） | 指标平台层（指标/维度） |
|---------|------------------|---------------------|
| 抽象层次 | 物理存储（ds.db.tbl.col） | 业务语义（GMV、活跃用户数、地区维度） |
| 使用场景 | SQL 查询、数据加工、表结构查看 | BI 分析、指标看板、指标字典 |
| 访问方式 | 直接 SQL `SELECT col FROM tbl` | 通过 DSL 选择指标+维度生成 SQL |
| 管控目标 | 谁能直接访问哪些物理数据 | 谁能在业务分析中使用哪些指标和维度 |

**举例说明**：
- 原子指标「GMV」绑定到底层字段 `orders.amount`，但用户有「GMV」指标的使用权 ≠ 他能直接 `SELECT amount FROM orders`。
- 维度「地区」映射到底层字段 `region`，但用户有「地区」维度的使用权 ≠ 他能直接 SQL 查询 `orders` 表的 `region` 字段。
- 反之，用户有 `orders` 表的 `region` 字段权限，也不代表他自动获得了「地区」维度在 BI 分析中的使用权限（维度还涉及显示字段、维表关联等业务定义）。

因此，指标平台需要**独立的一套权限管控体系**。

#### 5.3.2 指标平台权限模型

```
┌─────────────────────────────────────────────────────────────────────┐
│                    指标平台权限三层模型                               │
├─────────────────┬───────────────────────────────────────────────────┤
│  主题域权限      │  控制用户能否看到某个主题域及其下的指标            │
│  指标权限        │  控制用户能否查看/使用/编辑/发布某个指标            │
│  维度权限        │  控制用户能否查看/使用某个维度（含维度值查询）       │
│  修饰词权限      │  控制用户能否查看/使用某个修饰词                   │
└─────────────────┴───────────────────────────────────────────────────┘
```

**主题域权限（Subject Permission）**：
- 主题域是树形结构（如「电商 → 交易 → 订单」）。
- 上层主题域无权限则下层全部不可见。
- 权限级别：查看（可看到主题域及指标列表）、管理（可编辑主题域、分配指标归属）。

**指标权限（Metric Permission）**：

| 操作 | 原子指标 | 派生指标 | 复合指标 |
|------|---------|---------|---------|
| 查看（VIEW） | 查看指标定义、口径 | 查看指标定义、口径 | 查看指标定义、口径 |
| 使用（USE） | 在 BI 分析、指标看板中选用 | 在 BI 分析中选用 | 在 BI 分析中选用 |
| 编辑（EDIT） | 修改指标定义、口径 | 修改维度、修饰词组合 | 修改公式、引用指标 |
| 发布（PUBLISH） | 状态变更为已发布 | 状态变更为已发布 | 状态变更为已发布 |
| 下线（OFFLINE） | 状态变更为已下线 | 状态变更为已下线 | 状态变更为已下线 |

**维度权限（Dimension Permission）**：
- 查看（VIEW）：在维度管理页面看到该维度定义。
- 使用（USE）：在 BI 分析、指标分析中选用该维度做分组/筛选/排序。
- 维度值查询（VALUES）：查询该维度的枚举值列表（会触发对维表的 SQL 查询）。

**修饰词权限（Modifier Permission）**：
- 查看（VIEW）：看到修饰词定义。
- 使用（USE）：在派生指标定义或 BI 分析中选用该修饰词。

#### 5.3.3 维度权限 vs 表字段权限

这是最容易混淆的两个概念，必须严格区分：

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                           维度权限 vs 表字段权限                              │
├──────────────────────┬─────────────────────────┬─────────────────────────────┤
│                      │ 维度权限                 │ 表字段权限（元数据层）        │
├──────────────────────┼─────────────────────────┼─────────────────────────────┤
│ 权限对象              │ 业务维度（如「地区」）    │ 物理字段（如 orders.region） │
│ 配置位置              │ 指标平台 → 维度管理      │ 元数据平台 → 表结构管理      │
│ 使用场景              │ BI 分析选维度、指标看板   │ SQL 编辑器、数据加工任务      │
│ 数据访问方式          │ 通过指标 DSL 间接访问     │ 直接 SQL 访问               │
│ 权限继承关系          │ 不继承表字段权限          │ 不继承维度权限               │
│ 典型授权粒度          │ 维度编码（dimCode）       │ dsName.dbName.tblName.colName│
└──────────────────────┴─────────────────────────┴─────────────────────────────┘
```

**关键结论**：
1. **有维度权限 ≠ 有对应表字段权限**：用户可以在 BI 中按「地区」维度分组分析 GMV，但如果他没有 `orders` 表的 `region` 字段的元数据权限，他在 SQL 编辑器里写 `SELECT region FROM orders` 仍然会被拦截。
2. **有表字段权限 ≠ 有对应维度权限**：用户有 `orders.region` 字段的 SQL 查询权限，但如果他没有「地区」维度的使用权限，他在 BI 分析的维度选择器里看不到「地区」这个维度。
3. **为什么这样设计？**
   - 维度是「业务概念」，同一维度可能映射到多个不同表的字段（如「地区」可能在订单表、用户表、物流表都有）。维度权限管控的是「能不能在业务分析中使用这个业务概念」。
   - 表字段权限管控的是「能不能直接访问这个物理存储位置」。两者安全级别和管理目标不同。

#### 5.3.4 完全独立的两条权限线

指标平台权限与元数据权限**不仅是概念独立，在实际执行链路上也必须完全隔离**。核心原则：

> **用户申请了指标权限，不需要再申请表权限。指标 BI 分析的权限校验只走指标权限线，不走元数据权限线。**

**为什么必须完全隔离？**

| 反例场景 | 问题 |
|---------|------|
| 业务运营申请「华东区 GMV 指标」权限被通过 | 合理 |
| 业务运营在 BI 看板查看 GMV，但因为没有 `orders` 表的元数据权限而被 403 | **不合理**：用户感知不到底层表，申请流程也不应要求用户理解物理表结构 |
| 数据分析师有 `orders` 表的 SQL 查询权限 | 合理 |
| 数据分析师在 SQL 编辑器里写 `SELECT amount FROM orders` | 走元数据权限线，正常执行 |
| 数据分析师没有「GMV」指标的使用权限 | 合理 |
| 数据分析师试图在 BI 分析中选「GMV」指标 | 走指标权限线，被拦截 |

如果两套权限联动（如双闸门），指标平台的用户体验会被元数据层的规则不可预测地阻断，产品上是不可接受的。

**正确的架构：两条独立的权限线，统一的 SQL 改写中心**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    两条独立的权限线，SQL 改写统一由 dataauth 负责              │
├───────────────────────────────┬─────────────────────────────────────────────┤
│       元数据权限线             │           指标平台权限线                     │
├───────────────────────────────┼─────────────────────────────────────────────┤
│  使用场景：                     │  使用场景：                                  │
│  · SQL 编辑器                   │  · 指标 BI 分析（指标+维度组合查询）          │
│  · 数据加工任务                 │  · 指标看板                                  │
│  · 元数据表结构预览             │  · 维度值查询                                │
│  · 数据预览（元数据层）          │  · 指标字典                                  │
│                               │                                             │
│  前端入口：                     │  前端入口：                                  │
│  · /sql-editor                 │  · /bi/chart/analyzer                        │
│  · /data-work                  │  · /metrics/analysis                         │
│  · /meta/...                   │  · /metrics/dashboard                        │
│                               │                                             │
│  业务服务：                     │  业务服务：                                  │
│  · cyan-dataman（数据管理）     │  · cyan-datametric（指标服务）               │
│  · cyan-dataworks（数据加工）   │                                             │
│                               │                                             │
│  权限校验：                     │  权限校验：                                  │
│  · 调用 cyan-dataauth          │  · 调用 cyan-dataauth                        │
│    校验表/字段/行/列权限        │    校验指标/维度/修饰词权限                   │
│                               │                                             │
│  SQL 改写：                     │  SQL 改写：                                  │
│  · 调用 cyan-dataauth          │  · 调用 cyan-dataauth                        │
│    /auth/filter/sql            │    /auth/metric/filter/sql                   │
│    dataauth 用元数据规则改写     │    dataauth 用指标规则改写                    │
│                               │                                             │
│  SQL 执行：                     │  SQL 执行：                                  │
│  · 调用 cyan-datagateway       │  · 调用 cyan-datagateway                     │
│    /gateway/sql/execute        │    /gateway/metric/execute                   │
│    纯执行，不改写               │    纯执行，不改写                            │
│                               │                                             │
│  权限配置位置：                  │  权限配置位置：                               │
│  · 权限管理 → 数据权限           │  · 权限管理 → 指标平台权限                    │
│  · 元数据平台 → 表结构管理       │  · 指标平台 → 指标定义/维度管理               │
│                               │                                             │
│  审批流程：                     │  审批流程：                                  │
│  · 申请「orders 表只读权限」     │  · 申请「GMV 指标使用权限」                   │
│  · 审批人：数据Owner             │  · 审批人：指标Owner / 主题域负责人           │
└───────────────────────────────┴─────────────────────────────────────────────┘
```

**关键约束**：
1. **`cyan-dataauth` 是唯一的 SQL 改写中心**：无论是元数据层还是指标层，原始 SQL 都发给 `dataauth`，由 `dataauth` 根据对应的规则库改写后返回。
2. **`cyan-datagateway` 只负责纯 SQL 执行**：两个入口（`/gateway/sql/execute` 和 `/gateway/metric/execute`）只做执行，不做权限校验，不做 SQL 改写。
3. 元数据链路和指标链路在 `dataauth` 内部有两套**完全隔离的规则库**，由不同接口访问，互不可见。
4. 如果 `dataauth` 的 SQL 改写接口判定无权限，直接返回拒绝，不会生成改写后 SQL。

#### 5.3.5 指标层权限的配置方式

**方式一：按主题域批量授权（推荐）**

```
角色「业务运营-华东区」
  ├── 主题域权限：电商 → 交易（查看）
  ├── 指标权限：该主题域下全部原子指标（查看+使用）
  │             该主题域下全部派生指标（查看+使用）
  ├── 维度权限：地区、品类、时间、渠道（查看+使用）
  └── 修饰词权限：华东区、美妆、个护（查看+使用）
```

**方式二：按指标/维度单独授权**
- 适用于敏感指标（如「客单价」「退货率」）需要更细粒度控制。
- 管理员可在指标定义页面直接配置「可见范围」：公开 / 指定角色 / 指定用户。

**方式三：Owner 自动授权**
- 指标的 `owner` 字段所有者自动拥有该指标的查看+使用+编辑权限（减少配置量）。
- 主题域的负责人自动拥有该主题域下全部指标和维度的查看+使用权限。

#### 5.3.6 前端联动表现

| 页面 | 权限控制表现 |
|------|------------|
| 指标概览 / 指标字典 | 无主题域权限的指标卡片不显示；无查看权限的指标置灰或隐藏 |
| 指标分析 / BI 图表分析 | 指标选择器只列出有「使用」权限的指标；维度选择器只列出有「使用」权限的维度 |
| 维度值下拉框 | 查询维度枚举值前校验「维度值查询」权限；无权限时下拉框禁用并提示申请 |
| 指标定义页 | 无「编辑」权限时，「保存」「发布」按钮置灰；无「查看」权限时页面 403 |
| SQL 编辑器 | 与指标平台权限无关，走元数据层权限（表/字段/行列过滤） |

### 5.4 权限审批（Approval Workflow）

#### 5.4.1 审批场景

| 场景 | 审批类型 | 说明 |
|------|---------|------|
| 功能权限申请 | 角色变更审批 | 申请加入某个角色 |
| 数据权限申请 | 表级权限审批 | 申请某张表的读/写权限 |
| 数据权限申请 | 行级权限审批 | 申请某个行级规则的权限 |
| 数据权限申请 | 白名单审批 | 申请脱离某条脱敏规则 |
| 权限续期 | 到期续期审批 | 权限到期前自动提醒，申请续期 |

#### 5.4.2 审批流程设计

```
用户提交申请
    │
    ▼
┌─────────────────┐
│  自动审批引擎    │  ← 低风险规则自动通过（如申请自己负责业务域的只读权限）
│  · 规则匹配      │
│  · 风险评分      │
└────────┬────────┘
         │
    ┌────┴────┐
    ▼         ▼
 低风险      中/高风险
 自动通过     │
              ▼
         选择审批人
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
 直属上级   数据Owner   安全管理员
              │
              ▼
         审批决策
    ┌─────────┼─────────┐
    ▼         ▼         ▼
   通过      驳回      转交
    │         │         │
    ▼         ▼         ▼
 自动授权   返回原因   下一审批人
```

**审批节点配置**：

| 参数 | 说明 |
|------|------|
| 审批人 | 直属上级 / 数据Owner / 指定角色 / 指定用户 |
| 审批方式 | 会签（全部通过）/ 或签（任一通过） |
| 超时处理 | N 小时未审批自动转交 / 自动驳回 / 自动通过 |
| 审批条件 | 按资源敏感等级、申请人职级、申请范围大小动态匹配审批流 |

#### 5.4.3 我的权限 / 权限申请（用户侧）

**我的权限页面**：
- 展示当前用户拥有的全部权限（功能权限 + 数据权限），按模块分类。
- 展示权限有效期（永久 / 到期日）。
- 支持「一键续期」（触发续期审批流）。
- 支持「主动释放」（释放不再需要的权限，帮助减少权限膨胀）。

**权限申请页面**：
- 按数据源 → 数据库 → 表浏览数据资产（只显示已有元数据的资产）。
- 选择目标资源后，系统自动推荐需要的权限类型（只读/读写）。
- 填写申请理由，提交后展示审批进度（待审批 / 审批中 / 已通过 / 已驳回）。

```
│   ├── 列级脱敏（脱敏规则的配置与管理）

├── 指标平台权限
│   ├── 主题域权限（按主题域批量授权）
│   ├── 指标权限（按指标单独授权或按主题域批量授权）
│   ├── 维度权限（维度使用权限与维度值查询权限）
│   └── 修饰词权限（修饰词使用权限）
├── 审批管理
│   ├── 待我审批
│   ├── 我已审批
│   └── 审批流配置
├── 审计日志
│   ├── 访问日志
│   ├── 操作日志
│   └── 告警规则
└── 我的权限（用户视角，所有用户可见）
    ├── 我的功能权限
    ├── 我的数据权限
    └── 权限申请
```

### 6.2 各模块权限联动点

| 模块 | 联动点 | 权限生效方式 |
|------|--------|------------|
| 元数据平台 | 数据源树、数据库列表、表列表 | 无权限的数据源/库/表不显示 |
| 元数据平台 | 表结构详情页、数据预览 | 预览时自动注入行级过滤 + 列级脱敏 |
| SQL 查询 | 左侧数据源树 | 只显示有权限的数据源和表 |
| SQL 查询 | SQL 执行 | 执行前权限校验，执行时 SQL 改写 |
| SQL 查询 | 结果导出 | 导出需单独校验「导出权限」 |
| 指标平台 | 指标列表 / 指标字典 | 无主题域/指标查看权限的指标不显示 |
| 指标平台 | 指标分析 / BI 图表分析 | 指标选择器、维度选择器只显示有使用权限的项；执行时走指标权限线（不校验元数据表权限） |
| 指标平台 | 维度值下拉框 | 查询前校验维度值查询权限；无权限禁用并提示申请 |
| 数据加工 | 任务编辑 / 发布 | 生产环境任务自动校验账号权限 |
| BI | 数据集 / 图表 / 看板 | 数据集字段按列级脱敏规则展示；行级过滤自动注入 |

### 6.3 关键页面原型描述

#### 页面 1：角色管理

- **列表**：展示角色名称、描述、成员数、权限数、创建时间。
- **新增/编辑**：
  - 基本信息：名称、标识、描述。
  - 功能权限：树形选择器勾选菜单/按钮/API。
  - 数据权限：选择数据源/库/表，设置读写级别。
- **成员管理**：为角色添加/移除用户（支持按部门批量添加）。

#### 页面 2：行级权限配置

- **列表**：权限名称、关联表数、规则数、授权对象数、状态（启用/停用）。
- **新增/编辑**：
  - 步骤1 基本信息：名称、描述。
  - 步骤2 控制字段：选择字段、字段类型。
  - 步骤3 管控规则：可视化规则编辑器（类似 Query Builder），支持 AND/OR 嵌套、条件拖拽。
  - 步骤4 关联表：从元数据中选择表，系统自动匹配字段名和类型。
  - 步骤5 授权对象：选择用户/角色/部门/用户组。

#### 页面 3：列级脱敏配置

- **列表**：规则名称、关联表、生效字段数、授权对象范围。
- **新增/编辑**：
  - 选择关联表。
  - 为每个字段配置：默认规则（禁止查看/脱敏/明文）、按角色差异化规则。
  - 白名单配置。

#### 页面 4：指标平台权限配置

- **主题域权限配置**：
  - 左侧展示指标主题域树，右侧展示已授权的角色/用户。
  - 支持按主题域批量授权（勾选主题域 → 选择角色 → 确定权限级别：查看/使用/管理）。
- **指标权限配置**：
  - 列表展示指标名称、编码、主题域、状态、可见范围（公开/指定角色/私有）。
  - 支持批量修改指标的可见范围。
- **维度权限配置**：
  - 列表展示维度名称、编码、分类、关联字段、授权对象。
  - 支持单独配置「维度值查询」权限开关（默认关闭，需单独申请）。

#### 页面 5：我的权限（用户侧）

- **功能权限卡片**：以模块为单位展示已拥有的功能权限（如「元数据平台-只读」）。
- **数据权限卡片**：展示有权限的数据源/库/表列表，点击可查看具体行级规则和脱敏规则。
- **指标平台权限卡片**：展示有权限的主题域、指标、维度列表。
- **权限申请入口**：「申请新权限」按钮，引导至数据资产浏览器（元数据）/ 指标资产浏览器（指标平台）。
- **审批进度**：列表展示正在审批中的申请单及当前节点。

## 七、后端服务规划（cyan-dataauth）

### 7.1 服务定位

`cyan-dataauth` 作为**独立权限中心服务**，负责：
- 权限策略的存储与管理
- 权限校验（对外提供 RPC/HTTP 接口）
- 审批工作流引擎
- 审计日志采集与存储
- SQL 改写规则生成（供 SQL 网关层调用）

### 7.2 核心领域模型

```
User（用户）
  ├── id, staffNumber, cnName, deptId, jobTitle
  
Group（用户组）
  ├── id, name, type（DEPT/ROLE/CUSTOM）
  ├── members: User[]
  
Role（角色）
  ├── id, name, code, description
  ├── permissions: Permission[]
  
Permission（权限项）
  ├── id, resourceType（MENU/BUTTON/API/DATASOURCE/DB/TABLE/ROW/COLUMN/SUBJECT/METRIC/DIMENSION/MODIFIER）
  ├── resourceId, action（VIEW/USE/EDIT/EXECUTE/EXPORT/ALL）
  ├── conditions: JSON（ABAC 条件）

MetricPermission（指标权限项）
  ├── id, metricId / subjectId（指标ID或主题域ID，按主题域批量授权时填subjectId）
  ├── permissionType（SUBJECT / METRIC / DIMENSION / MODIFIER）
  ├── actions: Action[]（VIEW / USE / EDIT / PUBLISH / OFFLINE / VALUES）
  ├── targets: Target[]（授权对象：用户/角色/部门/用户组）
  ├── ownerAutoGrant: boolean（Owner是否自动拥有全部权限）
  
Policy（策略）
  ├── id, name, type（ACCESS/ROW_FILTER/MASKING）
  ├── priority（优先级，数字越小越高）
  ├── rules: Rule[]
  ├── targets: Target[]（授权对象）
  
Approval（审批单）
  ├── id, applicant, type, resource, status
  ├── workflow: WorkflowNode[]
  
AuditLog（审计日志）
  ├── id, userId, action, resource, result
  ├── sql（改写后）, ip, timestamp, riskLevel
```

### 7.3 对外接口设计（关键）

| 接口 | 用途 | 调用方 |
|------|------|--------|
| 接口 | 用途 | 调用方 |
|------|------|--------|
| 接口 | 用途 | 调用方 |
|------|------|--------|
| **元数据权限接口** |||
| `POST /auth/check` | 校验用户是否有某元数据资源的某操作权限 | cyan-dataman、cyan-datagateway（sql入口） |
| `POST /auth/filter/sql` | 输入原始 SQL + 用户信息，返回元数据层改写后的 SQL | cyan-dataman、cyan-dataworks（生成SQL后调用，获取改写后SQL再发给gateway执行） |
| `POST /auth/filter/rows` | 返回某表的元数据层行级过滤条件（WHERE 子句） | cyan-dataman（数据预览） |
| `POST /auth/filter/columns` | 返回某表的元数据层列级脱敏规则 | cyan-dataman（数据预览）、前端组件 |
| `GET /auth/resources` | 返回用户有权限的元数据资源树 | 前端数据源选择器（SQL编辑器） |
| **指标平台权限接口** |||
| `POST /auth/metric/check` | 校验用户是否有指标/维度的某操作权限 | cyan-datametric（BI分析前校验） |
| `GET /auth/metric/list` | 返回用户有权限的指标/维度列表 | 前端指标选择器、维度选择器 |
| `POST /auth/metric/filter/sql` | 输入指标业务 SQL + 用户信息，返回指标层改写后的 SQL | cyan-datametric（生成SQL后调用，获取改写后SQL再发给gateway执行） |
| **通用接口** |||
| `POST /approval/submit` | 提交权限申请 | 前端「我的权限」页面 |
| `GET /audit/logs` | 查询审计日志 | 前端审计日志页面 |

### 7.4 与现有服务的集成关系

```
cyan-dataauth（权限中心）
    │
    ├─← cyan-dataman-web（前端）调用：权限查询、元数据资源树、指标/维度列表、申请提交
    │
    ├─← cyan-dataman（数据管理后端）调用：功能权限校验、元数据资源权限校验
    │
    ├─← cyan-datagateway（SQL网关）调用：
    │     · 【sql入口】SQL 改写、执行前元数据层权限校验
    │     · 【metric入口】SQL 改写、执行前指标层权限校验
    │
    ├─← cyan-datametric（指标服务）调用：
    │     · 指标BI分析前：校验用户是否有指标/维度的 USE 权限
    │     · 指标/维度列表查询：过滤无 VIEW 权限的项
    │     · 维度值查询：校验是否有 VALUES 权限
    │
    ├─← cyan-dataworks（数据加工后端）调用：任务发布权限校验
    │
    └─← 员工服务（Employee）同步：用户、部门、职级信息

【两条完全独立的调用链】

链 A：SQL 编辑器 / 数据加工（元数据权限线）
    │
    ▼
cyan-dataman-web / cyan-dataworks
    ├── 前端/任务提交原始 SQL
    │
    └── 调用 cyan-datagateway 的 /gateway/sql/execute
            │
            ▼
    cyan-datagateway（sql 入口）
        ├── 调用 cyan-dataauth：校验元数据表/字段/行/列权限
        ├── 调用 cyan-dataauth：获取元数据层 SQL 改写规则（行过滤+列脱敏）
        ├── 无权限 → 拒绝执行
        └── 有权限 → 执行改写后的 SQL
            │
            ▼
        下发到 StarRocks 执行 → 返回结果

链 B：指标 BI 分析（指标平台权限线）
    │
    ▼
cyan-datametric（指标BI分析服务）
    ├── 调用 cyan-dataauth：校验指标/维度/修饰词权限
    │   ├── 无权限 → 直接返回 403
    │   └── 有权限 → MetricSqlBuilder 生成业务 SQL
    │
    └── 调用 cyan-datagateway 的 /gateway/metric/execute
            │
            ▼
    cyan-datagateway（metric 入口）
        ├── 调用 cyan-dataauth：校验指标/维度权限（再次确认）
        ├── 调用 cyan-dataauth：获取指标层 SQL 改写规则（可选，如指标层行过滤/列脱敏）
        ├── 无权限 → 拒绝执行
        └── 有权限 → 执行 SQL（不校验元数据表字段权限）
            │
            ▼
        下发到 StarRocks 执行 → 返回结果
```

## 八、非功能性需求

### 8.1 性能

- 权限校验接口 P99 < 50ms（策略缓存本地 + Redis）。
- SQL 改写接口 P99 < 30ms。
- 审计日志写入异步化，不影响主流程。
- 资源树查询支持懒加载，单节点展开 < 200ms。

### 8.2 安全

- 权限服务自身需鉴权，接口调用需带 Service Token。
- 审计日志不可篡改，支持归档到独立存储（如 OSS / S3）。
- 敏感操作（如超级管理员变更、策略删除）需二次确认 + 记录到审计日志。
- 权限缓存需有失效机制和一致性保障。

### 8.3 兼容性

- 功能权限对现有页面零侵入：通过前端路由守卫 + 按钮级权限组件实现。
- 数据权限对现有 SQL 查询零侵入：通过 SQL 网关层拦截改写实现。
- 存量数据迁移：默认所有现有用户保留当前全部功能权限（过渡期），数据权限默认拒绝（需主动申请）。

### 8.4 扩展性

- 策略引擎支持插件化扩展（未来可接入标签策略、动态脱敏 UDF）。
- 审批流支持 BPMN 规范，未来可对接企业 OA 系统。
- 审计日志支持对接外部 SIEM / 安全运营平台。

## 九、迭代规划

### Phase 1：基础权限（MVP，4~5 周）

**目标**：功能权限 + 表级权限 + 指标平台基础权限 + 基础审批 + 审计日志，解决「谁能看到什么菜单、谁能访问什么表、谁能用什么指标」。

| 模块 | 功能点 |
|------|--------|
| 功能权限 | 角色管理、用户-角色绑定、菜单/按钮权限控制、路由守卫 |
| 数据权限-L3 | 表级权限配置（按表授权：拒绝/只读/读写）、资源树按权限过滤 |
| 指标平台权限-L1 | 主题域权限（按主题域批量授权）、指标权限（查看+使用）、维度权限（查看+使用） |
| 审批 | 权限申请表单、审批流（直属上级 → 数据Owner）、我的权限页面 |
| 审计 | 登录日志、操作日志、访问日志记录与查询 |
| 前端 | 新增「权限管理」模块（角色管理、用户权限、指标平台权限、审批管理、审计日志、我的权限） |
| 后端 | cyan-dataauth 服务搭建，核心领域模型，权限校验接口，员工服务同步 |
| 指标服务联动 | cyan-datametric 集成权限校验：指标/维度列表过滤、BI 分析前权限校验 |

### Phase 2：行列级权限 + 独立链路落地（6~8 周）

**目标**：行级过滤 + 列级脱敏 + SQL 改写引擎 + 指标平台权限深化，实现「同一 SQL 不同人看到不同结果」，同时完成两条独立权限执行链的落地。

| 模块 | 功能点 |
|------|--------|
| 行级权限 | 行级规则配置（可视化规则编辑器）、SQL WHERE 注入、多表关联 |
| 列级脱敏 | 脱敏规则库、字段级规则配置、白名单、SQL SELECT 改写 |
| SQL 网关-sql入口 | cyan-datagateway 集成元数据权限校验 + SQL 改写，SQL 编辑器结果自动生效 |
| SQL 网关-metric入口 | cyan-datagateway 新增 `/gateway/metric/execute` 入口，只校验指标/维度权限，不校验元数据表权限 |
| 元数据联动 | 表结构预览、数据预览自动注入行列权限 |
| 指标平台权限-L2 | 维度值查询权限、修饰词权限、Owner 自动授权、按指标单独授权 |
| 独立链路落地 | 指标分析走 metric 入口（只校验指标权限）；SQL 查询走 sql 入口（只校验元数据权限）；两条链路完全隔离 |
| 审批增强 | 行级/列级/白名单/维度值查询申请、审批流配置化 |

### Phase 3：智能权限治理（持续优化）

**目标**：降低管理成本，提升安全水位。

| 模块 | 功能点 |
|------|--------|
| 智能审批 | 基于资源敏感等级 + 申请人属性的自动审批规则 |
| 权限洞察 | 权限使用热力图、闲置权限识别、冗余权限推荐回收 |
| 敏感数据扫描 | 自动识别敏感字段并推荐脱敏规则（扫描-脱敏一体化） |
| 告警中心 | 异常访问实时告警（如非工作时间大量导出、越权尝试） |
| 数据分类分级 | 按业务/安全维度给数据资产打标签，标签驱动权限策略 |

## 十、风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| SQL 改写引入性能损耗 | 高 | 改写规则缓存；复杂 SQL 采用子查询包裹而非字符串替换；提供性能开关 |
| 权限策略膨胀导致校验变慢 | 中 | 策略优先级 + 范围索引；本地缓存 + 增量同步；定期清理无效策略 |
| 存量用户权限降级导致业务中断 | 高 | 过渡期：存量用户默认保留全部功能权限，数据权限需主动开启；灰度上线 |
| 多引擎 SQL 方言差异 | 中 | SQL 改写引擎抽象方言层；优先支持 StarRocks / MySQL / PostgreSQL |
| 审批流阻塞业务效率 | 中 | 预设自动审批规则（低风险自动通过）；审批超时自动处理策略 |
| 指标入口被绕过直接访问元数据 | 高 | metric 入口只允许来自 cyan-datametric 的服务调用（Service Token 白名单）；metric 入口内禁止反向解析出原始表字段做元数据权限校验；审计日志完整记录所有 metric 入口的查询 SQL |
| 两条独立链路的管理成本 | 中 | 统一在「权限管理」页面管理两套权限，降低用户学习成本；权限策略模板化，减少重复配置；指标层的行级/列级规则优先采用「主题域批量授权」减少单条配置量 |
