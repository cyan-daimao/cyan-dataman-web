# 多事实表关联分析：竞品调研与综合方案设计

> 调研范围：Tableau、Power BI、网易有数BI、Superset/Metabase、StarRocks、字节Data Agent、Databricks、Oracle BI
> 调研重点：多事实表查询方案、物化视图/预计算、用户自定义报表固化

---

## 一、竞品多事实表查询方案

### 1. Tableau — Data Blending（数据混合）

**核心思想：先聚合，再关联（Aggregate Then Join）**

- 主数据源和辅助数据源**分别独立查询、聚合**，然后按公共维度字段进行 blending
- 本质上是 **LEFT JOIN on aggregated data**
- 各表保留自己的原始粒度，查询时自动聚合到视图粒度

```
事实表A ──► 聚合查询A ──┐
                        ├──► 按维度键 LEFT JOIN ──► 最终结果
事实表B ──► 聚合查询B ──┘
```

**优势：**
- 天然支持不同粒度的数据组合，避免数据膨胀（fan-out）
- 无需预处理，拖拽即可使用

**限制：**
- 只能做 LEFT JOIN（主表必须包含所有维度值），不支持 FULL OUTER JOIN
- 非加性聚合（COUNT、MEAN、MEDIAN）在 blending 后结果不准确
- 辅助数据源不能有 LOD（Level of Detail）表达式

### 2. Tableau — Relationships（关系模型，推荐方式）

- 在数据源层面定义逻辑表之间的"关系"（Noodles），而非物理 JOIN
- 查询时智能判断各表的粒度，分别聚合后再组合
- 自动处理 fan-out 和 chasm trap 问题
- **这是 Tableau 当前推荐的默认方式**，替代传统的 JOIN 和 Blending

### 3. Power BI — 星型模型 + DAX 跨粒度计算

- 标准做法：多个事实表通过共享维度表（星型模型）关联
- 不同粒度时，使用 DAX 的 `TREATAS` 或 `USERELATIONSHIP` 函数
- 或者构建桥接表（Bridge Table）处理多对多关系
- **业内批评**：Power BI 缺乏原生 multi-pass SQL 支持，复杂场景需要 DBA 预建视图或 Cube

### 4. 网易有数BI — 关系模型（最贴近我们方案）

**核心思想：先聚合后关联，保留每个表的详细级别数据**

> "对于不同粒度事实表一同分析的场景，可以通过定义数据关系，在分析时支持保留每个表的详细级别数据，使数据查询实现先聚合后关联，并规避数据膨胀和性能问题。"
> ——《有数BI用户手册》

- 在数据模型上增加"关系层"，配置逻辑表之间的关联
- 查询时各事实表在各自粒度上聚合，然后按维度外键关联
- **与我们的方案A思路完全一致**

### 5. Superset / Metabase

- **Superset**：在 SQL Lab 中支持手写 SQL JOIN 多表，但基于 Dataset 的图表构建不支持跨虚拟数据集 JOIN
- 用户需要先通过 SQL Lab 创建虚拟数据集（Virtual Dataset），然后基于此创建图表
- **Metabase**：查询构建器仅支持单表或预定义关系的表；复杂 JOIN 需写原生 SQL
- 两者本质上是**让用户自己写 SQL 解决多表问题**

### 6. Kimball 维度建模理论

> "如果用户频繁组合多个业务流程的数据，那么可以构建一个二级合并事实表（consolidated fact table），将数据一次性合并进去，而不是让用户自己用 SQL 去 drill across。"
> ——《The Data Warehouse Toolkit》

- 对于"不密切相关的底层流程"，用 SQL drill across（即我们的方案A）更合理
- 对于"频繁组合"的场景，应该预构建合并事实表（即我们的方案C）

## 二、竞品的物化视图/预计算方案

### 1. 网易有数BI — 物化视图（最详尽）

**实现：**
- 物化视图本质：预计算保存 SQL 查询的结果数据
- 分类：单表物化视图 / 多表物化视图；明细物化视图 / 聚合物化视图
- 更新策略：全量更新、增量更新
- 支持从报表"一键生成"物化视图

**痛点与解决：**
1. 多表关联查询慢 → 物化视图预计算 JOIN + AGG
2. 只查部分却扫全部 → 物化视图仅物化需要的字段和筛选条件
3. 筛选需求因人而异 → 物化视图支持带筛选条件的预计算

**查询改写（Query Rewrite）：**
- 校验阶段：聚合状态校验、关联校验、子查询递归校验
- 改写阶段：模型替换、字段替换、等价优化（聚合退化、谓词抵消）
- **查询时长下降10倍**

### 2. StarRocks — 异步物化视图

**语法：**
```sql
CREATE MATERIALIZED VIEW mv_name
REFRESH ASYNC START('2023-07-28 10:00:00') EVERY (INTERVAL 1 HOUR)
AS SELECT ...;
```

**特性：**
- **自动刷新（ASYNC）**：基表数据变化后自动触发刷新
- **定时刷新（SCHEDULE EVERY）**：按固定间隔刷新，无变化不触发
- **手动刷新（MANUAL）**：外部调度框架触发
- **分区刷新**：支持时间序列表的分区增量刷新
- **查询改写**：StarRocks 自动判断查询能否命中物化视图
- **嵌套物化视图**：支持多层物化视图，建议不超过3层

### 3. Databricks — Materialized Views

- 通过 Unity Catalog 管理
- 支持增量刷新（incremental refresh）和全量刷新（full refresh）
- 支持 CRON 表达式配置刷新计划：`ALTER MATERIALIZED VIEW ... ADD SCHEDULE USING CRON '0 0 * * *'`
- 由 Lakeflow pipeline 管理刷新任务
- 适用于 ETL 处理、BI Dashboard 加速

### 4. 字节Data Agent — 预置宽表

- 预先构建宽表（将多表 JOIN 结果物化为单表）
- 用户查询时通过 NL2SQL 转换为单表查询
- **局限**：宽表构建耗费大量人力，无法穷举场景，数据冗余，灵活性差
- **启示**：我们的方案不应走"预置宽表"路线，而应让用户按需物化

### 5. Oracle BI Server — Query Cache

- 本地磁盘缓存查询结果集
- 支持手动清除、自动清除（基于事件表）、编程式清除
- 需要评估数据新鲜度的可接受程度
- **启示**：缓存/物化需要考虑数据时效性

## 四、综合方案设计

### 核心理念

> **"先让数据说话，再让性能说话"**
>
> 用户先做即席分析（方案A），确认报表价值后，一键固化为物化视图（方案C）。
> 从"探索"到"固化"的自然演进，兼顾灵活性和性能。

### 一期：多事实表关联分析（方案A — CTE + FULL OUTER JOIN）

**目标**：支持用户将不同事实表的指标按相同维度进行分析

**SQL 生成逻辑**：

```sql
-- 假设：事实表A（订单表）+ 事实表B（退款表），按用户维度分析

WITH fact_a_agg AS (
    SELECT 
        user_id AS dim_key,
        SUM(order_amount) AS metric_1,
        COUNT(DISTINCT order_id) AS metric_2
    FROM iceberg.ods.orders
    WHERE date >= '2024-01-01'
    GROUP BY user_id
),
fact_b_agg AS (
    SELECT 
        user_id AS dim_key,
        SUM(refund_amount) AS metric_3,
        COUNT(DISTINCT refund_id) AS metric_4
    FROM iceberg.ods.refunds
    WHERE date >= '2024-01-01'
    GROUP BY user_id
),
joined AS (
    SELECT 
        COALESCE(a.dim_key, b.dim_key) AS user_id,
        a.metric_1,
        a.metric_2,
        b.metric_3,
        b.metric_4
    FROM fact_a_agg a
    FULL OUTER JOIN fact_b_agg b ON a.dim_key = b.dim_key
)
SELECT 
    d.user_name,
    d.user_level,
    j.metric_1,
    j.metric_2,
    j.metric_3,
    j.metric_4
FROM joined j
LEFT JOIN iceberg.dim.users d ON j.user_id = d.user_id;
```

**关键技术点**：

1. **指标按事实表分组**：根据 `MetricAtomicExt.dbName.tblName` 将指标分到不同事实表组
2. **维度外键映射**：通过 `metadata_table_relation` 查询每个事实表到维度表的外键字段
3. **CTE 子查询**：每个事实表独立生成聚合子查询，仅 SELECT 该事实表的相关指标
4. **FULL OUTER JOIN**：按维度外键 FULL OUTER JOIN，确保两边数据都不丢失
5. **维度表 LEFT JOIN**：最后 LEFT JOIN 维度表取显示名称等维度属性
6. **NULL 值处理**：未匹配到的指标列显示为 NULL（前端可显示为 `-` 或 `0`）

**适用场景**：
- 不同事实表有共同维度（如用户、商品、地区）
- 各事实表粒度相同或可按维度粒度聚合
- 即席分析、探索性查询

**性能预期**：
- 2个事实表 + 1个维度表：秒级（StarRocks）
- 3个及以上事实表：取决于数据量和过滤条件，可能需要物化加速

### 二期：用户自定义物化视图（方案C — 一键固化）

**目标**：用户确认报表有价值后，一键创建物化视图，定时刷新，提升性能

**交互流程**：

```
用户配置指标+维度 → 预览SQL → 执行查询（方案A）
    ↓（用户满意，点击"固化报表"）
弹出物化配置面板
    ├─ 物化视图名称
    ├─ 刷新策略：每日 / 每小时 / 手动
    ├─ 数据保留：最近7天 / 30天 / 全部
    └─ 确认创建
    ↓
后台执行：
    1. 基于当前SQL创建 StarRocks 物化视图
    2. 注册到元数据平台（作为"虚拟表"管理）
    3. 配置定时刷新任务（XXL-JOB / SchedulerX）
    4. 后续查询自动路由到物化视图
```

**StarRocks 物化视图创建示例**：

```sql
CREATE MATERIALIZED VIEW mv_user_order_refund_daily
COMMENT '用户订单退款日报'
DISTRIBUTED BY HASH(user_id) BUCKETS 16
REFRESH SCHEDULE START('2024-01-01 02:00:00') EVERY (INTERVAL 1 DAY)
AS
SELECT 
    user_id,
    dt,
    SUM(order_amount) AS total_order_amount,
    COUNT(DISTINCT order_id) AS total_order_count,
    SUM(refund_amount) AS total_refund_amount,
    COUNT(DISTINCT refund_id) AS total_refund_count
FROM ...  -- 方案A的完整SQL
GROUP BY user_id, dt;
```

**技术要点**：

1. **物化视图元数据管理**：
   - 新建 `bi_materialized_view` 表，记录：
     - `id`, `name`, `source_sql`, `mv_table_name`
     - `refresh_strategy`（MANUAL / HOURLY / DAILY / WEEKLY）
     - `last_refresh_time`, `next_refresh_time`, `status`
     - `creator`, `created_at`, `updated_at`

2. **刷新调度**：
   - 使用现有 `cyan-dataworks` 调度能力（XXL-JOB）
   - 或集成 StarRocks 原生 SCHEDULE 刷新
   - 建议采用"外部调度 + StarRocks 原生"双保险

3. **查询路由**：
   - 查询时优先检查是否有可用物化视图
   - 若物化视图数据新鲜度满足要求，直接查物化视图
   - 否则回退到实时查询（方案A）
   - 利用 StarRocks 的查询改写能力自动命中物化视图

4. **生命周期管理**：
   - 用户可手动刷新、暂停刷新、删除物化视图
   - 系统定期清理过期/未使用的物化视图
   - 物化视图失败时通知用户和管理员

### 三期：智能物化推荐（远期规划）

**目标**：系统自动识别高频查询模式，推荐或自动创建物化视图

- 分析查询日志，识别"高频 + 慢查询"的多事实表查询模式
- 自动推荐物化视图配置
- 用户一键确认即可创建

## 五、方案决策总结

| 阶段 | 方案 | 目标 | 技术路线 | 交付物 |
|------|------|------|----------|--------|
| 一期 | 方案A | 支持多事实表即席分析 | CTE + FULL OUTER JOIN | 多事实表查询SQL生成器 |
| 二期 | 方案C | 报表性能固化 | StarRocks 物化视图 + 定时刷新 | 物化视图管理模块 |
| 三期 | 智能推荐 | 自动化性能优化 | 查询日志分析 + 自动MV | 智能物化推荐引擎 |

**核心价值主张**：

> 不强迫用户在做分析之前就决定"要不要物化"。
> 让用户先自由地探索数据，当报表被验证有价值后，再提供一键固化的能力。
> 从"探索"到"生产"的无缝衔接。
